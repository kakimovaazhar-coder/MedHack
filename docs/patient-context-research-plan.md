# История пациента: приватность, выбор контекста и план следующего этапа

Дата исследования: 30 сентября 2026. Статус: предложение для согласования.
Этот документ не меняет код, API или режим хранения. README не изменяется.

## 1. Результат исследования

Предлагаемая функция: по текущей жалобе пациента или вопросу врача найти релевантные
записи этого пациента и показать краткую сводку с датами и проверяемыми источниками.
Система помогает подготовиться к приёму и оформить документ, но не устанавливает
диагноз и не считает старые назначения действующими без подтверждения.

Ограничение «не храним персональные данные» нужно сформулировать точнее:
**сервис не создаёт собственный постоянный архив идентифицируемой медицинской истории
вне контура клиники; основная история и соответствие идентификаторов остаются в МИС.**
Временная обработка медицинского текста всё равно является обработкой данных.
Если запрещена даже передача текста за пределы клиники, внешняя LLM для реальных
приёмов не подходит: обработчик и модель должны работать в разрешённом контуре.

### Хэш — не шифрование и не гарантия анонимности

Обычный SHA-256 от последовательного ID или ИИН можно атаковать перебором возможных
значений. NIST отдельно рассматривает keyed hash, включая HMAC-SHA-256 с секретным
ключом, как способ псевдонимизации. Это не устраняет риск узнавания человека по
содержанию истории. [NIST SP 800-188](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-188.pdf)

Руководство ICO различает псевдонимизацию и анонимизацию; таблицу соответствия нужно
держать отдельно. Это технический ориентир, а не утверждение о применимости британского
законодательства к проекту в Казахстане.
[ICO](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/data-sharing/anonymisation/pseudonymisation/)

Статья 273 Кодекса РК относит к медицинской тайне не только имя, но и сведения
об обращении, состоянии здоровья, диагнозе и лечении. Удаление ФИО не является
основанием обещать отсутствие чувствительных данных.
[Кодекс РК, статья 273](https://old.adilet.zan.kz/rus/docs/K2000000360)

Требования к месту хранения, основаниям обработки и трансграничной передаче должны
быть проверены для конкретной схемы клиники до подключения реальных данных.
Полный актуальный текст закона о персональных данных через просмотрщик «Әділет»
получить стабильно не удалось; юридическое соответствие этой архитектуры не подтверждено.

### OpenAI API не равен отсутствию хранения

В документации различаются сохранённое состояние приложения и журналы контроля
злоупотреблений. По умолчанию такие журналы могут включать запросы/ответы и храниться
до 30 дней, с оговорёнными исключениями. `store: false` не заменяет Zero Data Retention;
для ZDR требуется одобрение, применимость зависит от функций и настроек.
Для текущего MVP в облако допускаем только синтетические примеры. Нельзя утверждать,
что реальная история не покидает клинику, если она передаётся внешнему API.
[OpenAI: Data controls](https://developers.openai.com/api/docs/guides/your-data)

## 2. Идентификаторы: предлагаемая схема

1. Врач открывает пациента в МИС. МИС проверяет его право доступа.
2. Шлюз клиники создаёт случайный непрозрачный идентификатор сессии и привязывает его
   к пациенту, врачу, организации, сроку действия и разрешённым операциям.
3. MedHub получает контекст разрешённой сессии. Реальный patient_id, ИИН и ФИО остаются
   в МИС/шлюзе клиники; их не нужно пересылать сервису для поиска по истории.
4. Шлюз сам выбирает записи нужного пациента. Присланный из браузера ID не является
   доказательством права доступа. На каждый запрос проверяются сессия и полномочия.
5. LLM получает обезличенный в пределах принятой политики текст и временные ссылки
   `DOC_1`, `DOC_2`. Постоянный patient_id или patient_ref ей не нужен.
6. Шлюз связывает подтверждённый результат с пациентом и отправляет в МИС.

Сам session_id не должен быть единственным секретом, дающим доступ. Нужны
аутентификация врача/сервиса и серверная проверка связи с пациентом. Защита объекта
проверяется независимо от того, насколько сложно угадать его идентификатор.
[OWASP: Object Level Authorization](https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization/)

Если нужен устойчивый псевдоним между визитами, предпочтительно выдавать случайный
patient_ref на стороне клиники и хранить соответствие там. Альтернатива для обсуждения:
HMAC-SHA-256 от канонического набора `(версия, организация, внутренний ID)` с отдельным
секретом клиники. Ключ хранится в шлюзе, не в браузере и не у LLM. Ротация требует
версии ключа и плана сохранения связности. Стабильные псевдонимы не нужны для первого MVP:
прошлые записи можно каждый раз запросить из МИС через разрешённую сессию.

## 3. Где находятся данные

| Данные | Предлагаемое размещение | Жизненный цикл |
|---|---|---|
| ФИО, ИИН, исходный patient_id, соответствие сессии | МИС/шлюз клиники | По правилам клиники |
| Полные прошлые документы | МИС | Источник истины, без копии в архиве MedHub |
| Аудио и исходная расшифровка | Локальный обработчик клиники | Временно до проверки/отмены или истечения согласованного срока |
| Выбранные фрагменты истории и сводка | Память сервиса в разрешённом контуре | На время сессии, без кэша между пациентами |
| Черновик | Память сессии либо разрешённое хранилище клиники | Не хранить в облачной БД по умолчанию |
| Итоговый документ | МИС после подтверждения врача | По правилам клиники |
| Аудит действий | Контур клиники | Без полного текста в технических логах; сам аудит также требует защиты |

«Без постоянного хранения» затрагивает временные файлы, логи, трассировку, резервные
копии, браузерный localStorage, кэши и дампы. Таймер в приложении сам по себе этого
не гарантирует. Предлагается временный том/память с ограниченным сроком жизни, очистка
после сбоя и запрет записи клинических payload в телеметрию.

Удаление аудио сразу после распознавания конфликтует с прослушиванием источника:
в MVP разрешаем прослушивание до закрытия сессии и явно показываем срок доступности.
При строгом режиме только в памяти перезапуск теряет несохранённый черновик — этот
компромисс нужно показать пользователю. Долговечную очередь повторной отправки можно
организовать в контуре клиники; нельзя одновременно обещать её и нулевое хранение.

## 4. Как выбирать историю по текущему запросу

### Вход

Основание поиска — подтверждённый фрагмент текущего разговора и/или вопрос врача.
Например: «Раньше лечили анемию, снова слабость» или «Покажи предыдущие результаты
по анемии». Одна жалоба на слабость не должна превращаться в диагноз «анемия».
Тему поиска можно предложить автоматически, но врач видит и может изменить её.
Не использовать одну последнюю реплику без контекста: она может быть отрицанием,
исправлением или сообщением о родственнике.

### Конвейер

1. Проверить доступ врача и привязку сессии к пациенту/организации.
2. Локально извлечь тему, ключевые понятия, отрицания, время и говорящего.
3. Сформировать ограниченный поисковый план по разрешённым категориям.
4. Через адаптер получить только историю этого пациента. Ограничение по пациенту
   применяется до поиска/ранжирования, а не после получения общей выдачи.
5. Для анализов использовать структурированные поля, коды и даты; для текста —
   полнотекстовый поиск и словарь синонимов. При больших объёмах позднее можно добавить
   локальные embeddings и семантическое ранжирование.
6. Удалить дубликаты, учесть исправленные версии записей, выбрать релевантные фрагменты.
   Не сводить отбор к последним трём документам: нужный анализ может быть старше.
7. Сохранить дату, единицы измерения, статус результата и источник; явно отметить
   неполную выдачу/недоступный источник. Свежесть — фактор ранжирования, не доказательство
   актуальности диагноза или назначения.
8. Минимизировать и проверить текст перед LLM. Клинический текст и найденные документы
   считаются данными, а не инструкциями; модель не получает права выбирать другого пациента.
9. LLM пишет краткую сводку только по выбранным фрагментам. Каждое утверждение должно
   ссылаться на разрешённый source_id; числа и единицы сверяются с источником.
10. Врач видит сводку, причины выбора, источники и расхождения. Наличие ссылки само
    по себе не гарантирует верность вывода; итог остаётся на проверке врача.

Изоляция при поиске и проверяемые источники согласуются с рекомендациями
[OWASP RAG Security](https://cheatsheetseries.owasp.org/cheatsheets/RAG_Security_Cheat_Sheet.html).
Для модели данных можно ориентироваться на FHIR R4 Observation и DiagnosticReport:
показатель, значение, единица, клиническая дата, статус и исходный отчёт. Это внутренний
ориентир, не обещание наличия FHIR у UMC.
[Observation](https://hl7.org/fhir/R4/observation.html),
[DiagnosticReport](https://hl7.org/fhir/R4/diagnosticreport.html)

### Пример: запрос об анемии

Профиль поиска может включать прошлые заключения об анемии, гемоглобин/общий анализ
крови, ферритин и другие имеющиеся исследования обмена железа, записи о назначениях
и переносимости. Это поиск существующих сведений, не назначение новых исследований.
Медицинский словарь и критерии релевантности необходимо согласовать с врачом.
Ферритин, сывороточное железо и трансферрин — разные исследования, не синонимы.
[MedlinePlus: Iron Tests](https://medlineplus.gov/lab-tests/iron-tests/)

Нельзя приравнивать любую анемию к дефициту железа и отбрасывать документы о другой
причине: NIH описывает несколько типов анемии.
[NHLBI: Anemia](https://www.nhlbi.nih.gov/health/anemia)

Желаемый формат карточки (без выдуманных значений):

```text
По теме: анемия / предыдущее обследование
• Последний найденный гемоглобин: значение + единицы + дата + источник.
• Последний найденный ферритин: значение + единицы + дата + источник.
• В прошлой консультации указан препарат железа; текущий приём не подтверждён.
• Сегодня пациент сообщает, что прекратил приём — требуется уточнение.
```

Если результата нет в доступной истории: «Не найдено в доступных записях».
Если источник не ответил: «История сейчас недоступна». Эти состояния различаются.
Сравнение значений допустимо только при сопоставимых показателях и единицах; старые
лабораторные референсы переносить из отчёта, не придумывать универсальные нормы.

## 5. План реализации после согласования

| Этап | Изменение | Критерий готовности |
|---|---|---|
| 1. Граница хранения | Описать роли МИС/шлюза/MedHub, временную сессию, режимы synthetic_demo и clinic | Нет обещания анонимности только из-за ID; размещение каждого вида данных определено |
| 2. Контракт истории | Ввести структуры записи, источника, поискового запроса и сводки | Frontend получает примеры до появления LLM |
| 3. Mock МИС | Синтетические истории минимум двух пациентов, включая нерелевантные и старые документы | Запрос пациента A никогда не возвращает данные B |
| 4. Поиск контекста | Структурированные фильтры + словарь RU/KZ + ранжирование по теме/времени | На тестовом кейсе выбраны нужные документы без выдумывания фактов |
| 5. Сводка | Сначала проверяемый шаблон; затем LLM с тем же контрактом и ссылками | Можно открыть источник каждого факта; отсутствие данных показано честно |
| 6. Frontend | История и сводка слева, текущий разговор в центре, форма справа | Врач меняет тему поиска, открывает источник и видит одно расхождение |
| 7. Проверка | Доступ, точность отбора, полнота источников, удаление данных и время работы врача | Отчёт по тестам и измерениям без неподтверждённых процентов экономии |

Предлагаемые будущие маршруты (ещё не реализованы):

```text
POST /api/consultations/{id}/context-query
GET  /api/consultations/{id}/context
GET  /api/consultations/{id}/sources/{source_id}
```

Тело context-query: `focus_text`, `transcript_revision`, необязательный `time_range`.
Клинику, пациента и права backend получает из доверенной сессии, не из параметров LLM.
Для длительной обработки использовать существующий формат Job. Ответ контекста:
`query_revision`, `status`, `summary_items`, `evidence`, `conflicts`, `coverage`, `warnings`.
`query_revision` предотвращает показ старой сводки после смены темы. Coverage сообщает,
какие источники/период проверены, есть ли ограничения выдачи или ошибки доступа.

Точки изменения в существующем проекте:

- `schemas.py`: структуры контекста, источника и сессии; не просто переименование patient_id.
- `repository.py`: разделить постоянное хранение синтетического демо и временный режим;
  существующий SQLite сейчас сохраняет patient_id, транскрипт и поля формы.
- `integrations/`: добавить адаптер чтения истории и шлюз клиники.
- `services/`: поиск контекста, проверка источников, управление сроком жизни.
- `api.py`: доступ к контексту и источникам только в рамках разрешённой консультации.
- `contracts/`: новые модели и примеры для параллельной разработки frontend.

Первый демонстрационный кейс — запрос об анемии; три релевантных документа и несколько
отвлекающих, отсутствие одного анализа, расхождение по приёму препарата. Данные полностью
синтетические. Векторная БД, самостоятельные агенты с доступом к МИС, постоянная облачная
история и автоматическая постановка диагноза не входят в этот этап.

## 6. Что проверяем

- Подмена consultation_id, пациента, организации и source_id не открывает чужие данные.
- Отозванные права и истёкшая сессия блокируют дальнейшие запросы.
- Запись о родственнике и отрицание не превращаются в диагноз пациента.
- Старое назначение не становится текущим; исправленный лабораторный результат имеет приоритет.
- Нерелевантный текст и инструкции внутри медицинской записи не меняют доступ/поведение.
- У каждого факта есть разрешённый источник; значения/единицы не изменены.
- «Не найдено», «доступно частично» и «источник недоступен» отображаются по-разному.
- Тестовые идентификаторы не попадают в облачный payload, логи или browser storage.
- Закрытие/истечение сессии удаляет временные данные; отдельно проверить сбой/перезапуск.
- На размеченном наборе измерить долю нужных найденных документов, лишнюю выдачу,
  пропущенные значимые факты и неподтверждённые утверждения сводки.
- Сравнить время поиска истории и оформления вручную со временем через сервис,
  включая чтение, исправления и подтверждение. Учитывать эффект повторного знакомства с кейсом.

## 7. Что требуется согласовать до кода следующего этапа

Рекомендуемый MVP: синтетическая mock МИС, сессия вместо реального ID, поиск по теме,
источники и трёхколоночный UI. Для реального пилота отдельно выяснить доступный API МИС,
место развёртывания, разрешённые данные для внешнего LLM и политику сроков хранения.
Пока этих сведений нет, совместимость с UMC и юридическое соответствие не заявляются.
